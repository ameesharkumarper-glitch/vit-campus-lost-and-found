# 🎒 VIT Campus Lost & Found

A privacy-first recovery platform for the VIT community that replaces messy WhatsApp groups.
Students report lost/found items at official campus venues, owners prove ownership through a **private claim-check**, and returns are coordinated through an **in-app thread**, with no phone numbers exposed anywhere.

The whole project is a single notebook, `vit_campus_recovery.ipynb`, with a Flask + SQLite backend, an embedded single-page UI, and a **TensorFlow** lost↔found matcher.

---

## Features

| Area | What you get |
|---|---|
| **Venues & categories** | Separate **Lost** and **Found** feeds. Locations restricted to official landmarks: Academic Blocks (SJT, TT, PRP, SMV, MB, GDN, CDMM), Men's Hostels MH-A to MH-T, Ladies' Hostels LH-A to LH-J, Food Courts (Gazebo, Food Mall, DC), Central Library, Sports Complex. Categories: ID Cards, Room Keys, Calculators, Lab Equipment, Earphones, Wallets. Invalid venue/category is rejected by the API. |
| **Authentication & privacy** | Register with VIT e-mail (`@vitstudent.ac.in`), registration number and mobile. Passwords are hashed. Every user gets an anonymous alias (`Anon-7K2P`), the **only** identity other students ever see. Reg. no., e-mail and phone never appear in any API response. Posts containing phone numbers, e-mails or reg. numbers are rejected. |
| **Ownership verification** | The finder sets a challenge question ("What name/branch is on the ID tag?"). A claimant submits a *Claim Verification Request* with their answer, without seeing the finder's identity. The finder reviews answers in a private dashboard and **Approves** or **Rejects**. |
| **Safe handoff** | Approving a claim opens a private thread between the two parties. Either side proposes a staffed campus checkpoint (e.g. *SJT Ground Floor Reception*, *Central Library Security Desk*) and the other confirms. Phone numbers/e-mails are blocked in chat. |
| **Lifecycle** | Either the poster or the approved claimant can mark an item **Resolved**. It leaves the active boards, pending claims close, and the thread becomes read-only. |
| **TensorFlow matcher** | For any open post, "Suggest matches" ranks opposite-type posts using a Keras `TextVectorization` TF-IDF embedding, cosine similarity (`tf.linalg.l2_normalize` + `tf.matmul`), blended with category/venue agreement. Falls back to NumPy if TensorFlow isn't installed. |
| **UX feedback** | Skeleton loaders, empty states, retry banners, inline field errors, "Submitting…" button states, success toasts and confirmation panels. |

## Local setup

**Requirements:** Python 3.10 to 3.12, `pip`, and a modern browser.

```bash
git clone <your-repo-url>
cd <your-repo>

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

pip install jupyter flask werkzeug numpy tensorflow
```

> TensorFlow is large. If you skip it, the app still runs and the matcher uses the NumPy fallback. The "Suggest matches" panel reports which backend ran.

### Run it in Jupyter (recommended)

```bash
jupyter notebook vit_campus_recovery.ipynb
```

1. Choose **Run → Run All Cells**.
2. The database is bootstrapped automatically (cell 3).
3. The self-test cell prints `ALL TESTS PASSED ✅`.
4. The final cell starts the server. Open **http://127.0.0.1:5000**.
5. To stop it, run `stop_server()` in a new cell. To use another port, call `start_server(port=8000)`.

### Run it without Jupyter (headless)

```bash
jupyter nbconvert --to script vit_campus_recovery.ipynb   # creates vit_campus_recovery.py
# remove the leading "%pip install ..." line (a Jupyter magic) from the .py file
python -c "exec(open('vit_campus_recovery.py').read()); import time; time.sleep(10**9)"
```

## Database bootstrap

The schema lives in the notebook (`SCHEMA_SQL`) and is exported to `schema.sql` on first run. Bootstrapping is idempotent (`CREATE TABLE IF NOT EXISTS`).

| Method | Command |
|---|---|
| Automatic | Run notebook cell 3 (also re-run on server start) |
| Manual (SQLite CLI) | `sqlite3 vit_recovery.db < schema.sql` |
| Python | `bootstrap_db("path/to/file.db")` inside the notebook |
| Reset | Stop the server, delete `vit_recovery.db`, re-run cell 3 |

Tables: `users`, `items`, `claims`, `messages`. Indexes cover the feed and thread queries.

## Try the workflow (two browsers or one normal + one private window)

1. **Window A:** sign up as the finder (any `@vitstudent.ac.in` address, e.g. `24BCE1001`, 10-digit mobile starting 6-9).
2. **A:** *Report item* → **found** → category *ID Cards*, venue *SJT*, challenge "What name and branch are on the ID tag?"
3. **Window B:** sign up as the owner, open **Found**, view the item, answer the challenge, and submit.
4. **A:** *My dashboard* shows the claim from an alias. Click **Approve**.
5. **A or B:** *Open handoff chat*, propose *SJT Ground Floor Reception*, and confirm from the other side.
6. After meeting, either side clicks **Item returned. Mark resolved**. The post disappears from the boards.

## API reference

All responses are JSON. Errors look like `{"error": "message", "fields": {"title": "reason"}}` with HTTP 400/401/403/404/409/422/429.

| Method & path | Auth | Purpose |
|---|---|---|
| `POST /api/register` · `POST /api/login` · `POST /api/logout` · `GET /api/me` | – | Account session |
| `GET /api/meta` | – | Venues (grouped), categories, checkpoints |
| `GET /api/items?kind=lost\|found&category=&venue=&q=&page=` | optional | Public feed (open items only, alias-only posters) |
| `POST /api/items` | ✔ | Create a lost/found post |
| `GET /api/items/<id>` | optional | Item detail |
| `POST /api/items/<id>/claims` | ✔ | Submit Claim Verification Request |
| `GET /api/dashboard` | ✔ | Own posts with incoming claims, plus own claims |
| `POST /api/claims/<id>/decision` | poster | `{"decision": "approve" \| "reject"}` |
| `GET /api/claims/<id>/thread` | parties | Messages and checkpoint state (approved claims only) |
| `POST /api/claims/<id>/messages` | parties | Send chat message |
| `POST /api/claims/<id>/checkpoint` · `/checkpoint/confirm` | parties | Propose / confirm meetup point |
| `POST /api/items/<id>/resolve` | poster or approved claimant | Mark returned |
| `GET /api/items/<id>/matches` | poster | TensorFlow-ranked suggestions |

### Validation rules

| Field | Rule |
|---|---|
| E-mail | Must end with `@vitstudent.ac.in` |
| Registration number | `^\d{2}[A-Z]{3}\d{4,5}$` (e.g. `24BCE1234`) |
| Mobile | 10 digits starting 6-9 |
| Password | 8+ characters, letters and numbers |
| Title / description | 3-80 / 10-500 characters, no phone/e-mail/reg. no. |
| Venue / category | Must be in the official lists |
| Verification question (found) | 10-200 characters |
| Claim answer | 3-300 characters |
| Chat message | 1-500 characters, no phone numbers/e-mails |

Basic abuse limits: 5 failed logins per 5 minutes per e-mail, 10 posts/hour/user, 20 messages/minute/user.

## Privacy design

- Public endpoints serialise items through one function that only emits the poster's **alias**.
- Claimants never receive the finder's identity, and finders only see claimant aliases plus the answer text.
- Threads are accessible only to the two parties of an **approved** claim, and are read-only after resolution.
- Contact-info patterns are rejected in public text and in chat, nudging everyone toward the checkpoint flow.
- The notebook's self-test asserts that reg. numbers, e-mails, phones and real names never appear in public feeds or dashboards.

## Testing

Cell 7 (`run_self_test()`) runs an end-to-end scenario against a temporary database: validation failures, privacy leak checks, wrong vs right claimants, approval, chat filtering, checkpoint handshake, resolve semantics, and TF/NumPy matching. Re-run it anytime with `run_self_test()`.

## Production notes

- Set `SECRET_KEY` as an environment variable and serve behind HTTPS with a production WSGI server (e.g. `gunicorn`) instead of the notebook launcher.
- Add real e-mail verification (OTP to the VIT address) before going live. Registration currently validates the address format only.
- Swap SQLite for PostgreSQL if usage grows, and add server-side rate limiting (e.g. Redis) for multi-process deployments.
- Edit `VENUE_GROUPS` and `CHECKPOINTS` in cell 2 to match any campus changes.
